# 重构分阶段推出模式

当需要对 Backlog.md 的核心抽象层（如 ID 生成、搜索索引、内容存储）进行结构性变更时，采用分阶段子任务推进，避免一次性大面积修改导致的测试雪崩和回滚困难。

## 适用场景

- 数据模型重命名或拆分（如 `body` → `rawContent`）
- 全局配置项引入（如可配置 ID 前缀、DoD 默认值）
- 搜索/索引基础设施替换（如迁移到 Fuse.js 共享存储）
- 新增跨模块横切关注点（如 shell 补全支持多平台）

## 标准步骤

| 阶段 | 目的 | 关键产出 | 示例 |
|---|---|---|---|
| **Phase 0: 父任务定范围** | 明确影响面、依赖图、验收标准 | 带 ASCII 依赖图的父任务描述；子任务编号清单 | BACK-273, BACK-345, BACK-308 |
| **Phase 1: 奠基抽象层** | 创建所有下游依赖的阻塞性抽象 | 独立工具模块 / 类型定义，零消费者调用 | 345.01 `PrefixConfig`、273.01 `rawContent` 类型 |
| **Phase 2: 并行核心改造** | 独立子系统并行更新 | 多个互不依赖的 PR/子任务可并行开发 | 345.02 ID 生成 / 345.03 文件系统 / 345.04 加载器 |
| **Phase 3: 集成** | 将新抽象接入 CLI / Web / TUI | 端到端冒烟通过 | 345.06 UI/CLI、273.04 CLI&TUI、273.05 Server |
| **Phase 4: 高级功能** | 在新地基上构建此前无法实现的能力 | 利用新抽象的增值功能 | 345.07 promote/demote ID 重分配 |
| **Phase 5: 迁移与收尾** | 处理破坏性变更、回归测试、文档 | 自动迁移脚本、完整测试覆盖、用户手册更新 | 345.08 draft 前缀迁移、345.09 init 配置、308.07 文档测试 |

## 常见陷阱

| 陷阱 | 示例 | 预防 |
|---|---|---|
| **测试中硬编码引用雪崩** | BACK-345 在 ~500 处测试代码中硬编码了 `task-` 前缀，重构时需批量替换 | 在 Phase 1 就引入配置化前缀工具，测试中统一使用 `getPrefix('task')` |
| **Phase 1 抽象不够阻塞** | 若抽象层留有「后续再补」的接口，Phase 2 的消费者会各自 hack | Phase 1 的模块必须包含所有下游需要的方法，通过编译器/类型检查验证 |
| **遗漏迁移子任务** | BACK-345.08 是计划外追加的，因为用户反馈现有 `draft-` 文件散落在 `task-` 文件夹 | Phase 0 必须显式列出「是否需要数据迁移」checklist |
| **集成阶段才发现遗漏消费者** | BACK-273.04 发现 CLI 和 TUI 仍直接访问旧 API | Phase 0 用 `grep` 扫描所有 `import` 和调用点，列出完整影响半径 |
| **并行子任务间隐式依赖** | 两个子任务同时修改同一文件的相邻区域，合并时冲突 | 父任务中标注「文件级冲突风险」，建议串行或提前协调接口 |
