### 边界确认：MCP memo 分页 ≠ 网页端 memo 分页（两条独立路径）
用户问「memo 改动会不会影响网页端」。核验结论：**不影响**，两条路径在 core 分叉：

- **网页端**：`src/web/components/MemosPage.tsx`（无限滚动，靠 `feed.nextCursor !== null` 判 hasMore）→ `src/web/lib/api.ts:fetchMemosPage({limit,cursor,date})` → `GET /api/memos` → `src/server/index.ts:handleListMemos` → `src/core/memos.ts:listMemosPage(root,{limit,cursor,date})` → 返回 `{items, nextCursor}`。
- **MCP**：`memo_list` tool → `src/mcp/tools/memos/handlers.ts:listMemos()` → core `listMemos()`（全量，无分页）+ MCP 层 `selectListPage` → 返回 `{items,total,offset,limit,hasMore}`。

硬证据：`git status` 中 memo 相关改动只有 `src/mcp/tools/memos/handlers.ts`、`schemas.ts`、`src/test/mcp-memos.test.ts` 三个文件；`core/memos.ts` / `src/server/*` / `src/web/*` 零改动。limit 上限两边一致（100：网页端 `MAX_MEMO_PAGE_SIZE`，MCP schema `maximum:100`），但分页参数不互通（cursor vs offset）——各自自洽。

**关键教训**：初版我曾把 core `listMemosPage` 改成 offset 语义，那会**直接打断网页端**（api.ts 期待 `nextCursor`、MemosPage 靠它判 hasMore、server:2006 传 cursor）。已回退 core、把 offset 分页收敛进 MCP handler。**规则：core 的 memo cursor 契约是网页端 REST 的生命线，任何 MCP 侧分页需求都不得改 core。**

### 评估：offset 语义能否做无限加载（若将来网页端也 offset 化）
结论：能。无限加载与分页参数无关，offset 更简单（`nextOffset += items.length`，终止读信封 `hasMore`）。

本项目要点：
- **"深分页慢"这一经典 offset 缺点在本库不成立**：MCP 的 `selectListPage` 是内存 `slice`，core 的 `listMemosPage` 是 `findIndex`，两者都是每次全量读目录 + 排序 + 内存切片，每页成本同为 O(total)。
- **唯一真代价 = 并发写入漂移**：memo 降序（新在前，`core/memos.ts:147`），翻页间若有新增，整列后移 → offset 重复返回已加载项；有删除 → 漏项。cursor 用 id 锚点（`findIndex(cursor)+1`）不受影响。
- **重复恰好有既有兜底**：`src/web/utils/memos.ts:appendMemoPage` 已按 id 去重（`seen = Set(state.memos.map(m=>m.id))`），能吸收 offset 的重复；但**漏项兜不住**（去重只能处理重复）。
- **若网页端换 offset，改动面只有 2 处**：`MemosPage.tsx` 的 `loadMore`（`cursorRef` → 累加 offset，并去掉 `if (!cursor) return` 终止判断）与 `hasMore`（`feed.nextCursor !== null` → 信封 `hasMore`）；`appendMemoPage` 无需改动。`MEMO_FEED_PAGE_SIZE = 30`。

### 走过的两条错路（记住别再走）
1. **`git commit --fixup=26444c66a` + `rebase --autosquash` 不行**：fixup 的补丁是相对 **tip** 的，rebase 会把它当独立 item 重放到 737 上 → 4 处内容冲突 + 2 处 modify/delete 冲突（"deleted in HEAD" 就是在说那 2 个 737 时还不存在的文件）。
2. **`git apply --3way` 整包打也不行**：`git apply` 是原子的，一处失败全回滚；而且 --3way 会把「我的终态版本」（含 742 的 `offset`/`ListPage` API）塞进 737，产出不可编译的中间态。

### 正确做法
1. `git branch backup/pre-737-amend <old-tip>`、`git branch backup/fix-final <fix-tip>` 两个安全网；`git write-tree` 记下**目标树哈希**。
2. `git checkout --detach 26444c66a`（737 基线）。
3. 按文件拆补丁逐条 `git apply --3way`：**零漂移的 11 个文件直接干净落地**（`utils/date-utc.ts`、`date-display.ts`、`search-results.*`…）。
4. 有漂移的 4 个（`core/memos.ts`、`test/memos.test.ts`、`web/utils/memos.ts`、`web/utils/memos.test.ts`）**按 737 的代码手写这份修复**（例如 737 的 `listMemosPage` 是 cursor 版，只改那行 filter + 加 import），不要套补丁。

6. `git checkout --detach backup/pre-737-amend` 再 `git rebase --onto <new737> 26444c66a`：738–741 干净重放，**只有 742 在同样 4 个文件冲突**。因为 742 是最后改这批文件的提交，直接 `git checkout backup/fix-final -- <那批文件>` 取终态即可；`memos.md`/`mcp-memos.test.ts` 也一并归到 742（740 新建、742 又改过）。
